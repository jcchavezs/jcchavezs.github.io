If you contribute to GitHub from more than one identity — a personal account and
a work one, say — you have probably met this problem the hard way: a commit that
shows up under the wrong face, or worse, signed with the wrong key. Let me explain
why that happens, why there isn't an easy way around it.

![Image]({{ site.baseurl }}/images/2026-10-14-gh-auth.png)

## How does git deal with attribution?

Here is the thing most people never think about: GitHub doesn't decide who authored
a commit — `git` does, locally, before GitHub ever sees it. When you run
`git commit`, git stamps the commit with an author name and email taken straight
from your configuration:

```console
$ git config --global user.name "Jane Doe"
$ git config --global user.email "jane@example.com"
```

Those two values are baked into the commit object itself. (Technically a commit
carries both an *author* and a *committer*, but for everyday work they're the same
person and come from the same settings.) GitHub later takes the commit's author
email and looks for an account that has verified it — that's how a commit gets
linked to a profile and shows up on someone's contribution graph. No match, and the
commit shows up as an anonymous or unlinked author, even though the push itself was
authenticated.

Signing works the same way: it's a *git* setting, not a GitHub one. If you sign
commits, git reads your key and whether signing is on from config too:

```console
$ git config --global user.signingkey ABCD1234ABCD1234
$ git config --global commit.gpgsign true
```

The key takeaway: **your identity on a commit is a property of your local git
config, resolved at commit time.** It has nothing to do with how you authenticated,
or with any account you happen to be "logged in" as. Hold on to that — it's exactly
where things fall apart with multiple accounts.

## Can `gh` help?

[`gh`](https://cli.github.com) is GitHub's official command-line tool. It wraps the
GitHub API and the common workflows around it: authenticating, cloning, opening
pull requests, reviewing issues, managing releases, and so on. Instead of juggling
personal access tokens by hand, you run `gh auth login` once and `gh` keeps your
credentials, talking to the API on your behalf.

It is genuinely good at what it does. The trouble starts when "you" is more than
one person.

## The single-active-account model

`gh` does support multiple accounts. You can log into several and list them:

```console
$ gh auth status
github.com
  ✓ Logged in to github.com account personal
  ✓ Logged in to github.com account work
```

But notice the word *active*. At any moment, exactly **one** account is active,
and switching is a global, stateful toggle:

```console
$ gh auth switch --user work
```

This flips a single value in `~/.config/gh/hosts.yml`. There is no notion of "this
terminal is my work account and that terminal is my personal account." The active
account is a property of your whole machine, not of the shell, the directory, or
the repository you happen to be in.

That design has two painful consequences.

### 1. You cannot be two accounts at the same time

Open two terminals. In one you want to push to a work repo; in the other, to a
personal project. There is no way to pin each terminal to its own account —
`gh auth switch` in one window changes the active account for *both*. If you
background a long-running task under one identity and switch in another window,
you have quietly changed what the first one will do. For anything concurrent, the
single global switch is simply the wrong shape.

### 2. Your git identity drifts out of sync

Here is the subtler trap. `gh` controls which account the *API* uses. It does
**not** touch your `git` identity — `user.name`, `user.email`, and your signing
key. Those live in git config and change only when you change them.

So you run `gh auth switch --user work`, start committing, and every commit is
still stamped with your *personal* name and email, maybe even signed with your
personal GPG key. GitHub happily accepts the push; the attribution is just wrong.
You usually find out when a reviewer points at the author line, or when a signed
commit shows up as "Unverified" because the key doesn't match the account. The two
systems — `gh`'s active account and git's identity — have no idea the other exists.

## How did I solve it?

It started with [this hint](https://github.com/cli/cli/issues/12145#issuecomment-3532638758) buried in the gh CLI repository — enough to convince me the gap was worth closing properly.

So I spent a weekend hacking on it with Claude and shipped [`gh-auth`](https://github.com/jcchavezs/gh-auth): a small CLI that teaches `git` and `gh` to agree on which identity you're using.

Under the hood it leans on three tools you already have:

- **`gh`** to read the active account (`gh api user`) and switch (`gh auth switch`)
- **`git`** to read and write your identity configuration
- **`gpg`** to find a secret key matching the account's email and turn on commit signing automatically

### Two accounts at once, for real

The piece that fixes the concurrency problem is:

```console
$ gh-auth shell [profile]
```

This launches a shell with an isolated `GH_CONFIG_DIR`. Because the `gh`
configuration is scoped to that shell's environment rather than shared globally,
each shell can hold its own active account independently. Work account in one
window, personal in another, at the same time, without either one stepping on the
other. This is the per-shell isolation the stock `gh` model doesn't give you.

```console
$ gh-auth shell jcchavezs
Starting shell with profile jcchavezs.

Git author/committer name: jcchavezs
Git author/committer email: josecarlos.chavez@owasp.org
Git signing key: **redacted**
```
